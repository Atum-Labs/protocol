## [Unreleased]

### Added

- The Known to Atum v2 credential context, `https://schemas.atum.xyz/credentials/known-to-atum/v2`, is resolved beside v1. v2 defines every v1 term as v1 does and adds the `quoteAwarder` and `merchant` roles, which v1 does not define, so a credential issued under v1 for either role has a signature that does not cover its role. A holder credential naming v2 can be passed to `buildEnvelope` and `requestSessionToken`. Credentials naming v1 work as before, and a v1 credential for any other role signs the same bytes under either context. Earlier versions refuse a credential naming the v2 context with `unknown JSON-LD context`.
- `MISSING_QUOTE_SELECTOR`: the 400 a quote request gets when it names no `quote_selector`.
- `GetPaymentStatusResponse.refunded_amount` and `refund_partial`: on a `refunded` payment from Solana, what the escrow paid back in the source token's base units, and `refund_partial`, whether that was less than the deposit. Both are optional: `refunded_amount` is absent when unknown, and `refund_partial` is absent when the deposited amount is unknown. Only `GET /v1/payments/{paymentId}/status` carries them.
- `awardQuote` pays a Stellar quote: the deposit is signed for the quote's `source_amount` by the delegate signer, and the reserve by the `quote_selector`'s ed25519 key, which must be a `G...` account (pass its signer as `selectorSigner`). `AwardQuoteParams` takes `stellarRpcUrl`, `stellarClockReader`, `stellarDelegateEpoch`, `stellarDelegateEpochReader`, `stellarDelegateRecordReader` and `stellarSigningKey` as `preparePaymentRequest` does, so an award is refused before signing when the payer's delegate record is expired, spent or registered to another key than `stellarSigningKey`. It signs only the deposit digest of its message's own `message_prehash`, and refuses a depositor or selector signer bound to another network (`signer.network`); a signer with no `network` is admitted. A reserve signed by another key than the selector's is refused before the award is sent. As with `preparePaymentRequest`, an award signed by a separate delegate key is built and signed, but `verifyPaymentRequest` refuses it (`DelegateUnverifiedError`); only the payer's own key as its delegate verifies offline. This replaces the 6.0.0 note that `awardQuote` refuses a Stellar quote request, and that the payer's one-time `create_delegate` and SEP-41 `approve` are not built here.
- `createStellarDelegate`: a Stellar payer's one-time setup. It registers the delegate signer on the escrow (`create_delegate`), reads the record back, approves the escrow on the token (SEP-41 `approve`), and resolves to the `epoch` the escrow assigned, for `stellarDelegateEpoch`. Before submitting anything it refuses a limit, expiry or delegate key the escrow would refuse, and a payer that already has a delegate record for the token. The requested escrow must match the application's trusted deployment address. The SDK validates the prepared authorization and allowance lifetime before signing. `StellarDelegateSetupError` carries the creation hash and, when known, the `epoch` if record readback or approval cannot be confirmed after creation. `finishApprovalForEpoch` can finish approval for the original unspent delegate without replacing it. The delegate may be a separate key; a payment it signs is refused by an offline verifier, which admits only the payer's own key (see Stellar payments). It needs the optional `@stellar/stellar-sdk`.
- `error` on `QuoteRequestResponse` and `QuoteRequestStatusResponse`: why a quote request has no quotes, as the same `PaymentFailure` a failed payment carries. `NO_SETTLER_FOR_CORRIDOR` means no settler serves the source and destination pair, and `SERVICE_BUSY` means no capacity was available to start the auction. It is absent while the quote request is `collecting`, whenever a settler was asked, and when `requested_count` is absent for any reason other than `SERVICE_BUSY`, because whether a settler serves the pair is then unknown. Optional: earlier versions ignore it.

### Changed

- A payment request envelope (an envelope whose `type` declares `PaymentRequestEnvelope`) is no longer accepted with a holder signature in the settler identity EIP-712 form (`SettlerProof`). That form signs a settler's own envelopes, and no originator produces an envelope in it; settler envelopes keep it. Nothing in this package signs a payment request envelope in that form, so envelopes it builds verify as before.
- The bundled signing libraries accept a payer's wallet-signed proofs only where the verifier asks: the inner `PaymentRequest` proof signed as EIP-712 `PaymentRequestProof{proofHash, docHash}`, and a payment request envelope's holder proof signed as `PaymentRequestEnvelopeProof{proofHash, docHash}`, both under the `Atum Payment Request` domain. Both commit the same two Data Integrity hashes the raw form signs, so they bind the same request, challenge, domain, holder and credentials. They are off by default, and this package turns neither on: a wallet shows that typed data as two hashes, so a page that asks a payer to sign it obtains a valid proof over whatever document it hashed, and only a verifier of the originator's own payment request accepts it. Verification of every proof this package produced before is unchanged.
- Every bundled secp256k1 proof verifier, `verifyDeclaration` and `verifyFulfillmentQuote` included, refuses a recovery byte (`v`) other than 0, 1, 27 or 28. Earlier versions accepted 35 and above, and `verifyFulfillmentQuote` also 8 to 26. Every signer in this package writes 27 or 28, so proofs it produced verify as before.
- The package moved within the protocol repository, from `schemas/apis/payment-gateway/v1/bindings/payment-gateway-client/` to `schemas/apis/payment-gateway/v1/bindings/typescript/client/`, beside the other payment-gateway bindings split by language. Only the manifest `homepage` and `repository.directory` change; the published name, entry points and behavior do not.
- `CreateQuoteRequest.quote_selector` is documented as the account that signs the award's reserve: name it on every quote request, normally `source.account`. A quote request without it no longer stands for `source.account`. The field stays optional in the types; `prepareQuoteRequest` sets it in every release. The `quote_selector` description shared with `PaymentRequest` says what the field is, not a default.
- `awardQuote` throws when the quote request names no `quote_selector`, or names a blank one, before it signs or sends anything. It signed the reserve as the depositor; a quote request must now name its selector.
- The messages of `QUOTE_SELECTOR_NOT_ALLOWED` and `RESERVER_MISMATCH` no longer describe leaving `quote_selector` out. Codes and statuses are unchanged.
- A direct deposit re-submitted with only its deadlines moved is answered with the payment its `request_id` already holds, even under depositRequestHash version 2, where the moved deadlines name a deposit you did not fund. It used to get `409 IDEMPOTENCY_TERMS_MISMATCH`. Check that the returned `payment_id` is the id of the deposit you funded: the direct-deposit table in `docs/idempotency.md` says what to do when it is not, and adds the `409 CONFLICT` answer, which the `409` description on `submitPayment` now documents too. Types are unchanged.
- The `403` description on `submitPayment` and `awardQuote` lists the codes a payment refused before it is created can carry: `AUTHORIZATION_DECLINED`, and the new `AMOUNT_LIMIT_EXCEEDED` (over the per-payment amount limit for the paying account) and `VOLUME_LIMIT_EXCEEDED` (over the paying account's daily limit, which resets at 00:00 UTC). A payment refused for a dollar limit used to arrive as `AUTHORIZATION_DECLINED`; branch on `code` to tell the three apart. The `ApiError` the client throws for a `403` carries this description as its `message`. Types are unchanged.
- The `SERVICE_BUSY` message for an auction that could not start for lack of capacity says "this request" instead of "this payment", because a quote request can carry it too. The code, HTTP status and `retry_classification` are unchanged.
- When a quote request has an `error`, `request-quote` prints its code and message in place of "Try again", so a source and destination pair no settler serves is not retried as is, and `quote-status` adds the code to its header and the message below it. Output is unchanged when there is no `error`.

## [6.0.0] - 2026-11-16

> **Breaking: the generated award types follow the new award request.** `BidAward`, `AwardResponse`
> and `AwardAccepted` are removed, and the generated `quoteRequests.awardQuote` resolves to
> `PaymentResponse`. Only code that awards quotes is affected.
>
> **Breaking: the payment body type.** `SubmitPaymentData.requestBody` (TypeScript) and
> `SubmitPaymentJSONRequestBody` (Go) are now `SubmitPaymentRequest`, whose `sender_auth` is
> optional for a payment you fund yourself.
>
> **Breaking: `max_source_amount` must be whole digits**, the rule the gateway already applies to
> `fulfillment_amount`. The gateway spec now states the rule for both fields on all three request
> bodies that carry them.
>
> **New: session tokens.** `createSessionTokenSource` keeps a session token current for the
> Payment Gateway, bound to a key the client holds (DPoP). See [Session tokens](docs/signing.md#session-tokens).
>
> **New: awarding quotes and direct deposits.** `awardQuote` and the `award-quote` command award a
> chosen quote, and `prepareDirectDepositRequest` builds a payment your wallet funds itself.

### Added

- `requestSessionToken`, `signSessionPresentation` and `SessionTokenError` in the `./signing` entry: request a session token from the Atum authorization service by presenting the Known to Atum credential issued to your wallet, and send it to the Payment Gateway as `Authorization: Bearer`. Each call to the service is abandoned after `timeoutMs` (10 seconds by default). `createSessionTokenSource` keeps a token current for a long-running client: pass it to `PaymentGatewayClient` as the new `session` option. It renews in the background before expiry, and a failed renewal never fails a gateway call. A call made with no valid token waits for the session for at most `maxWaitMs` (2 seconds by default, `DEFAULT_MAX_WAIT_MS`), then goes without one. Its tokens are bound by default to a key it holds (RFC 9449 DPoP), so each request carries `Authorization: DPoP` with a fresh proof; where the authorization service does not bind tokens they are sent as `Bearer`. `createDPoPKey` and `createDPoPProof` are the binding on its own, and `requestSessionToken` takes a key as `dpop`. See [Session tokens](docs/signing.md#session-tokens).
- `PaymentSummary.display_max_source_amount`: `max_source_amount` formatted in the source asset.
- `PERMIT_TOKEN_MISMATCH`: the 400 an award gets when `sender_auth` authorizes a token other than the quote request's source asset.
- `VerifyPaymentRequestExpectations.quoteSourceAmount`: for a deposit that pays a chosen quote, `verifyPaymentRequest` and `verifyPaymentRequestJSON` bind the permit amount to exactly that quote's `source_amount` instead of `max_source_amount`.
- `prepareDirectDepositRequest`: builds a payment your wallet funds itself, with `approve` and the escrow's `directDeposit`, instead of a Permit2 signature. It returns the request, which carries no `sender_auth`, the `deposit` it names, and the `depositRequestHashVersion` the deposit commits: `deposit.input` is what `directDeposit` takes, `deposit.depositId` is the payment id, and `deposit.unreserved` is what `refundUnreserved` needs to return an unreserved deposit. It signs nothing and sends nothing. Leave `depositRequestHashVersion` unset and the deposit commits the version the gateway publishes for the source chain, so a deposit you prepare after the gateway moves to version 2 commits version 2 with no change on your side. A deposit you funded but had not yet submitted when the gateway changed version names no payment and comes back only through `refundUnreserved`, so keep the time between preparing and submitting as short as finality allows. Each refusal is a `DirectDepositError`, thrown before anything is returned: `reason` `gateway_version` for a version you pass that differs from the published one, `version_unpublished` for no version from a gateway that publishes none (a gateway that predates the member: pass the version its operator gives you), `version_unknown` for a published version this release cannot commit, whatever you pass, and `version` for a version other than 1 or 2, before any network call. Version 1 is deprecated for direct deposits: every deposit at version 1 carries `deprecation`, and passing version 1 yourself also emits a `DeprecationWarning` with the code `ATUM_DIRECT_DEPOSIT_V1`, once per process; under `--throw-deprecation` the method rejects with that warning instead, so you can catch it. When the deposit commits version 1 the `requestId` must be a UUIDv4 from `randomUUID()`, since the deposit commits only its hash; under either version keep it undisclosed until you submit. `depositNonce` is required and has no default, and so are both deadline windows: build once with a quote window longer than the deposit takes to become final, and submit the same request once it is final, with a short quote window remaining. The source must be an ERC-20 on an EVM chain. It checks the request against the rules the gateway applies, including the EIP-55 checksums of the depositor, escrow, quote selector and verifier account, before returning it, so a malformed request is refused before you fund rather than after. See [Funding the deposit yourself](README.md#funding-the-deposit-yourself) and [Direct deposits](docs/idempotency.md#direct-deposits).
- `directDepositRequestHashVersion` on `ChainDefaults`, read from the new `direct_deposit_request_hash_version` of `GET /v1/defaults`: the depositRequestHash version the gateway derives a direct deposit's id at, published for EVM chains. `prepareDirectDepositRequest` follows it when you pass no version. It is absent from a gateway that predates the member, and otherwise carried as published, a version this release does not know included, which `prepareDirectDepositRequest` refuses rather than build at another. Read it fresh for each direct deposit, `resolvedDefaults` included: defaults read before the gateway changed version still build at the old one.
- `encodeDirectDepositCalldata`: the calldata of the escrow's `directDeposit` for `deposit.input`.
- `deriveDirectDeposit`: the deposit a stored direct-deposit request names, for a payer that keeps the request JSON rather than the returned `deposit`, whose amounts are bigints. The `DirectDepositPaymentRequest`, `DirectDepositFulfill` and `SettlerRequirements` types are exported too.
- `PaymentRequestError`, `UnsupportedDestinationAssetError`, `DirectDepositRuleError` and `DirectDepositError`, so a refusal from `prepareDirectDepositRequest` can be told apart with `instanceof` and its `rule` or `reason` read. `DirectDepositReason` lists the reasons `deriveDirectDeposit` reports, and `DirectDepositClientReason` those and the three `prepareDirectDepositRequest` adds.
- `SubmitPaymentRequest`: the body `payments.submitPayment` takes. It is `PaymentRequest` with `sender_auth` optional, which only a payment you fund yourself may omit.
- `awardQuote` on `PaymentGatewayClient`: award the quote you chose from a quote request. It checks the quote against the quote request you sent, signs `sender_auth` for exactly the quote's `source_amount` with `depositorSigner`, signs `reserve_auth` with `selectorSigner` (the depositor's signer when the quote request names the depositor as `quote_selector`), and sends `POST /v1/payments/awards`. It resolves to `{ paymentId, response, request }`. A quote that carries `awarded_payment_id` skips the `award_deadline` check, so a retry reaches the gateway's replay after the deadline. See [Awarding a quote](docs/awarding.md).
- `quoteSelector` on `prepareQuoteRequest`: the account that signs the reserve when a quote is awarded, when it is not the depositor.
- `verifyFulfillmentQuote` in the `./signing` entry: checks a quote's settler signature and that its `quote_id` is the quote's hash, and returns the signer's DID.
- `award-quote` command: awards a quote with the same signing options, `--wait` and exit codes as `send-payment`. `award-quote --from <file> [quote_id]` awards from what `request-quote` printed, signing the quote request it sent; with no `quote_id` it awards the cheapest quote that can be awarded, which from a script needs the quote request to set `max_source_amount`, or at a terminal lets you pick one. At a terminal, `award-quote <quote_request_id> [quote_id]` awards without a file, the quote picked or named: it signs the quote request as the chosen quote carries it, after showing what you pay and asking, and only when that quote request names the escrow, fulfillment verifier and fulfillment proxy `/v1/defaults` lists. From a script it takes only `--from`. Before signing, it checks the quote's settler signature, that its `quote_id` is the quote's hash, and that the quote request's `settler_requirements` admit its signer. The `Pay …? [y/N]` line shows the `fulfillment_deadline`, after which an undelivered payment is refundable.
- At a terminal, `request-quote` lists the quotes cheapest first, lets you pick one with ↑/↓ and Enter while each quote's award window counts down, and pays it in the same run. Amounts read as tokens, `0.10015 USDC (100150 units)`, where `GET /v1/defaults` lists the token. Where keys cannot be read one at a time, it asks for a row number. Paying takes `--provider`, `--wait`, `--wait-for`, `--wait-seconds` and `--solana-rpc-url` as `send-payment` does. Quotes whose settler signature does not verify, or whose signer `--allow-settler` does not admit, are left out. From a script it refuses those options, and its JSON output adds `quote_request`, the body it sent, for `award-quote --from`. At a terminal, `quote-status` prints the quotes as a numbered table, and how to award one.
- `--allow-settler <did>` on `send-payment` and `request-quote`.
- Stellar payments: `preparePaymentRequest` builds a `STELLAR` deposit for a `stellar:<pubnet|testnet|futurenet|standalone>` source, with the escrow digest computed by the shared encoder, and `createSenderSigner` signs it with the delegate signer's ed25519 key (a 32-byte seed as 64 hex digits, which `verifyAddressMatchesKey` checks against `pinnedAddress` when one is given). `issued_at` is the latest closed ledger's close time (`stellarRpcUrl`, `stellarClockReader`). The digest commits to the `epoch` of the payer's delegate record: pass it as `stellarDelegateEpoch`, or `preparePaymentRequest` reads it from the escrow through the Soroban RPC (`stellarDelegateEpochReader`, or `stellarDelegateRecordReader` for the whole record, replaces the read), which needs the optional peer dependency `@stellar/stellar-sdk`; with no delegate registered it fails rather than assume an epoch. When the record is read, the build also refuses one the escrow would reject at `deposit`: an `expiration` at or before `issued_at`, no remaining capacity (a renounced record), and, when `stellarSigningKey` is given (`send-payment` passes the key it signs with), a registered signer that is not that key. A supplied `stellarDelegateEpoch` or an epoch-only `stellarDelegateEpochReader` reads no record, so none of these are checked. `signPaymentRequest` and `send-payment` sign a Stellar message only when it is the deposit digest of its own `message_prehash` under the request's network and escrow (`assertRequestSignable`, which `signPaymentRequest` runs for any request whose source is a `stellar:` network or whose signer is bound to one), because a Stellar key signs 32 bytes with plain ed25519, which is also how a transaction is signed, so a requester could otherwise set `message` to a transaction hash and receive the payer's signature on it. The private-key signer reports the network it is for as `signer.network`. `deterministicStellarNonce`, `generateStellarNonce` and `STELLAR_MAX_DEPOSIT_VALIDITY_SECS` are exported. `verifyPaymentRequest` admits a Stellar payment only when the signing key is the payer's own account, and refuses one signed by a separate delegate key, because the requester names that key and no offline check reads whether it is registered for the payer; the verified permit carries `delegateSigner`, `delegateEpoch` and `delegateOnchainUnverified: true`, since even the payer's own key is registered on chain, which an offline check does not read. `send-payment --delegate-signer` signs with a delegate key that is not the sender's own, for a verifier that reads the chain. Signing a Stellar message with Turnkey fails closed until Turnkey's Stellar address format is confirmed, and `awardQuote` refuses a Stellar quote request. The payer's one-time `create_delegate` and SEP-41 `approve` are not built here. No Atum production gateway lists a Stellar chain in `/v1/defaults` yet (read 2026-11-16).

### Changed

- **Breaking: the generated award types follow the new award request.** `AwardRequest` names the quote request and the chosen quote, `{request_id, quote_request_id, quote_id}`, and carries `sender_auth` and `reserve_auth`, plus `originator_auth`. The new `ReserveAuth` type is the reserve message the `quote_selector` signs, with `message_prehash` required. The generated `quoteRequests.awardQuote` resolves to `PaymentResponse`, held or not. `BidAward`, `AwardResponse` and `AwardAccepted` are removed.
- A Solana deposit signature is verified the way the Solana ed25519 program verifies it: `verifyPaymentRequest`, `verifyPaymentRequestJSON` and `verifyRequestCommitment` refuse a signature for a small-order public key, or one whose `R` is a small-order point. Ordinary wallet keys and signatures are unaffected; the program never accepted these.
- In the `./signing` entry, `verifyDeclaration` verifies an Ed25519 proof whose `verificationMethod` is a Stellar account (`did:pkh:stellar:<network>:G…`) as well as a Solana one; it refused every namespace but `solana`. Both return a `self-asserted-ed25519` signer, so if you accept only one chain, check that `signer.did` names it before relying on the key. Building and verifying a Stellar payment is described under Added.
- The error `verifyPaymentRequest` and `verifyPaymentRequestJSON` throw when the permit amount differs from `max_source_amount` is now named `PermitAmountMismatchError`. Its message is unchanged.
- `prepareQuoteRequest` names the depositor as `quote_selector`, or the account passed as `quoteSelector`. It named the gateway's selector from `GET /v1/defaults`, which cannot sign an award, and it now refuses that selector.
- `--whitelistSettler` is now `--allow-settler`. The old spelling still works and is no longer listed in `--help`.
- **Breaking for TypeScript callers: `SubmitPaymentData.requestBody` is now `SubmitPaymentRequest`**, and `sdkPaymentShadow` takes one. Passing a `PaymentRequest` still compiles. Code that reads `requestBody` as a `PaymentRequest`, such as a `PaymentsService` subclass that overrides `submitPayment`, has to handle a missing `sender_auth`.
- **Breaking for Go callers: `SubmitPaymentJSONRequestBody` is now `SubmitPaymentRequest`**, so a `PaymentRequest` no longer compiles as a `SubmitPayment` argument. Construct a `SubmitPaymentRequest`, setting `SenderAuth` to `&request.SenderAuth` for a signed payment or leaving it nil for a direct deposit. Rebuild an explicit `Executor` using `SubmitPaymentRequest_Executor` and its generated variants; the old struct cannot be directly cast to the new one.
- `preparePaymentRequest` refuses an `executor` that gives the deposit leg to the originator, before any network call, and points at `prepareDirectDepositRequest`: a Permit2-signed request cannot fund a deposit the originator makes.
- **Breaking: `max_source_amount` must be whole digits**, the rule the gateway already applies to `fulfillment_amount`. The PaymentRequest schema gives it `minLength: 1` and the pattern `^[0-9]+$`, so once the gateway runs this schema it refuses a request whose ceiling is a decimal, a sign, `NaN` or `Infinity` at decode, and the generated Go types refuse it on unmarshal. The gateway spec now states the rule for both fields on all three request bodies, `POST /v1/payments`, `/v1/payments/authorizations` and `/v1/payments/quote-requests`, and the exported `$PaymentRequest`, `$SubmitPaymentRequest` and `$CreateQuoteRequest` schemas carry it. A request that sends the ceiling as the token's smallest units, as this client always has, is unaffected. An empty `max_source_amount` is refused too, where the gateway treated it as no cap; omit the field to set no cap.
- The `quote_deadline` description on `PaymentRequest`, `SubmitPaymentRequest` and `CreateQuoteRequest` now gives the lower bound as well as the upper one. A window too short for a settler's work before quoting is declined `QUOTE_WINDOW_TOO_SHORT`, and the fix is a longer `quote_deadline`. Both bounds are counted from when a settler receives the request, and a direct deposit at `depositRequestHash` v2 fixes the deadline before the deposit. A payment is reissued only once it has failed, and a reissued direct deposit is a new deposit, so the first is recovered with `refundUnreserved` after the failure. A longer window declined with a reason whose `retry_classification` is not `NOT_RETRYABLE_FIX_REQUEST` is on the settler's side. `DEFAULT_QUOTE_DEADLINE_SECONDS` and `DEFAULT_PAYMENT_QUOTE_DEADLINE_SECONDS` no longer suggest 3 seconds is enough for every settler, the `quote_deadline_seconds` description on `PreparePaymentRequest` now warns that a short window can be declined `QUOTE_WINDOW_TOO_SHORT` and says to reissue with a larger value, and the README's direct-deposit rules say to reissue with a shorter or longer `quote_deadline` once the payment has failed and the deposit is refunded. Types and runtime behaviour are unchanged; only what the types say about them.

### Fixed

- `PaymentSummary.display_amount` is documented as formatted in the destination asset, the unit `fulfillment_amount` is in.
- In the `./signing` entry, signing and verifying with a Solana (Ed25519) or Tron key failed with `bs58` errors (`encode is not a function`): `signDeclaration`, `verifyDeclaration`, the identity envelope and session token presentations. They now work.
- The help of `send-payment` and `request-quote` describes `<amount>` as the amount the receiver gets, in the destination token's smallest units.
- `send-payment` and `approve-permit2` exit `1` with a message when stdin closes before a private key is entered. They exited `0` without doing anything, which `send-payment` uses for a completed payment.

## [5.0.0] - 2026-10-30

> **`send-payment --wait` now stops once the payout is on chain** (`finalizing`, exit code `5`)
> instead of waiting for `completed`. Pass `--wait-for completed` for the previous behaviour.

### Added
- `depositRequestHashVersions` on `ChainDefaults`, read from the new `deposit_request_hash_versions` of `GET /v1/defaults`: the versions a deposit from the chain may be signed with, `[1]`, `[1, 2]`, or `[2]` once the gateway no longer accepts v1. `preparePaymentRequest` signs v2 when it lists 2 and v1 otherwise, and refuses a chain whose list names no version this build signs. From a gateway that predates the member it reads `deposit_request_hash_version` as before.
- `xAtumProducer` and `xAtumDepositRequestHashV2` on `submitPayment`, and `submitPaymentShadow` and `sdkPaymentShadow`: the optional `X-Atum-Producer` and `X-Atum-Deposit-Request-Hash-V2` headers, used for compatibility diagnostics only; they never change how the payment is processed. `PaymentGatewayClient`'s `payments.submitPayment` sends them as `sdk-ts` unless the call names an `xAtumProducer`.
- `depositRequestHashV2Mode: 'retire'` on `verifyRequestCommitment`'s options: `enforce` that accepts only depositRequestHash v2, so a deposit committing v1 is refused as `request_hash_mismatch`. `verifyPaymentRequestJSON` does not take it.
- `send-payment --auto-accept`, and `autoAccept` on `submitPayment`: the gateway awards the first valid quote at or under `max_source_amount` instead of waiting for `quote_deadline`. Faster, but gives up competitive pricing.
- `STELLAR` in the `SenderAuthMessageScheme` type, and Stellar addresses in the OpenAPI address patterns: a `G...` account or `C...` contract strkey. A Stellar asset is `stellar:<pubnet|testnet>/sep41:<C... contract id>`, which `parseAssetIdentifier` already accepts. The package does not build or verify Stellar payments yet.
- `send-payment --wait-for <finalizing|completed>`, which implies `--wait`.
- `waitForStatus`, the same function as `waitForTerminalStatus` under a name that does not promise a terminal state.
- `waitFor: 'finalizing' | 'completed'` on `waitForStatus`, and the `WaitFor` type; any other value throws. The default is `'completed'`, as before. `--wait-for` defaults to `finalizing` instead, because the command line now answers as soon as the payout is on chain (see Changed). The wait now also stops at `refund_available` (see Changed).
- `deposit_nonce` on the `PaymentRequest` type: the nonce an originator-executed deposit (`executor.deposit: "originator"`) passed to the escrow's `directDeposit`, as a decimal string of at most 78 digits.

### Changed
- The default fulfillment deadline is 5 minutes (`DEFAULT_FULFILLMENT_DEADLINE_SECONDS` is `300`), where it was 1 hour, in `preparePaymentRequest`, `prepareQuoteRequest`, `send-payment` and `request-quote`, and the API description's default for `fulfillment_deadline_seconds` on `PreparePaymentRequest` is `300`. A failed payment's refund no longer waits an hour, and a successful payment is just as fast. A `fulfillmentDeadlineSeconds` you pass is used unchanged. For a large payment, pass a longer one (for example `3600`): a settler may wait until the source chain finalizes a large deposit, and does not bid on a deadline that wait does not fit.
- Both deadline windows count from when the request is built, and the payout has to fit in what is left after the quote window. A `quoteDeadlineSeconds` of `300` or more without a longer `fulfillmentDeadlineSeconds` is now refused before anything is built, where the limit used to be `3600`, and the error says when the fulfillment window it names is the default. When you raise `quoteDeadlineSeconds`, raise `fulfillmentDeadlineSeconds` (`--fulfillment-deadline-seconds`) by the same amount.
- `defaultGateway` (and `OpenAPI.BASE`) is generated from `schemas/apis/hosts.yaml` and is always the payment-gateway testnet URL. It is no longer a hand-copied literal.
- `PaymentsService.submitPayment` now documents its `500` and `502` answers, so the `ApiError` message for either status says when to reconcile by `payment_id` before acting. The `PaymentFailure.code` docs list `QUOTES_EXPIRED` and `NO_SETTLER_FOR_CORRIDOR`, which arrive as a `failed` payment, never as an HTTP error.
- `PaymentsService.submitPayment` now documents its `422`: `INSUFFICIENT_FUNDS` or `MISSING_TOKEN_APPROVAL` when the paying account could not fund the deposit. `PaymentFailure.code` lists both.
- **Breaking: `send-payment` exits `5` for a `finalizing` payment** (paid on chain, not yet final), with or without `--wait`. It used to exit `2`. A script that treats `2` as "keep waiting" must handle `5` too. `payment-status` still exits on whether the lookup worked; its summary now says the payment is not yet final and names the payout transaction.
- **Breaking: `send-payment --wait` stops at `finalizing`** instead of waiting for `completed`. Pass `--wait-for completed` for the previous behaviour.
- **Breaking: `waitForStatus`, `waitForTerminalStatus` and `send-payment --wait` stop when the payment reaches `refund_available`**, where they used to keep checking until the budget ran out. The refund is waiting on the payer, so waiting longer does not help. The outcome then has `timedOut: false`, but the payment is not final: it can still become `completed` if a late delivery is paid. Read `snapshot.status` before treating it as failed.
- **Breaking: a payment request whose `executor` is the string `"originator"`, or an object giving every leg to the originator, is refused** by the PaymentRequest rules the gateway runs, where it used to validate. Both give the deposit leg to the originator, and an originator-executed deposit (`directDeposit`) is reserved by the settler and names its `deposit_nonce`. To give only the fulfill leg to the originator, pass `executor: { deposit: 'settler', reserve: 'settler', fulfill: 'originator' }`. The builders never set `executor` themselves; only a caller passing one of these forms is affected.
- `computeRequestHash` covers `deposit_nonce`: two requests that differ only in it now hash differently, where both used to hash alike. Requests without the member hash as before.
- `computeRequestHash` hashes a request without `sender_auth`, as the schema and the Go binding already allow (an originator-executed deposit carries none). It used to throw `missing required field sender_auth`.

### Deprecated
- `waitForTerminalStatus`: use `waitForStatus`, the same function.

### Removed
- **Breaking: `fulfillment_confirmation` is no longer part of `PaymentResponse`, `GetPaymentStatusResponse` or `AwardResponse`, and the `FulfillmentConfirmation` type is gone with it.** Its transaction details are in `transactions`: the source hash, chain and block in `transactions.deposit`, and the destination ones in `transactions.fulfillment`. `PaymentResponse` and `GetPaymentStatusResponse` carry `transactions`; for an award, read it from `GET /v1/payments/{paymentId}/status`. `payment_id` is on every response; `request_id` is the one you submitted, so keep it alongside the `payment_id`. Read `status` to decide whether a payment completed, and `transactions` for its hashes. Unlike the confirmation, `transactions` gains each stage as it happens, including on a payment that never completes.

## [4.0.0] - 2026-10-16

### Added
- `preparePaymentRequest` signs depositRequestHash v2, the hash of the payment terms, when the source chain's `GET /v1/defaults` entry says so. The new `deposit_request_hash_version` on that response is read into `ChainDefaults.depositRequestHashVersion`; absent is 1, and v1, `keccak256(request_id)`, stays the default. A caller passing `resolvedDefaults.source` sets it there.
- `verifyPaymentRequestJSON` and `verifyRequestCommitment` read depositRequestHash v2 when asked: `depositRequestHashV2Mode: 'audit' | 'enforce'` on the expectations, or as the new `options` argument of `verifyRequestCommitment`. Either mode accepts a deposit committing v1 or v2; `audit` admits a request the strict reader refuses and reports why in `strictDetail`, `enforce` refuses it as `request_malformed`. Without it, both behave exactly as before. Opted in, `CommitmentResult` carries `depositRequestHashVersion` (`v1` or `v2`) and `expectedDepositRequestHashV2`, and `VerifyResult` carries the check's result as `commitment`.
- `capFromQuote(sourceAmount, slippageBps)` derives a `max_source_amount` from a settler's quoted `source_amount` plus a slippage tolerance in basis points (0 to 10000). Both amounts are in the source token's smallest units, so no decimals or price are involved, and the result rounds up so it never falls below quote plus tolerance. A non-canonical amount or an out-of-range slippage throws.
- `preparePaymentRequest` leaves `executor` off unless the caller passes it. Omitted on the wire means settler. Pass `{ deposit, reserve, fulfill }` to split the legs. The request `version` is the declaration bindings constant, `1.3`, because `executor` is a new field.

### Changed
- `PaymentStatus` gains `refunding`, `refund_available` and `refunded`, so a caller branching exhaustively on it needs the new values. `GetPaymentStatusResponse.refund_signature` is present only on `refund_available` and lets the originator submit the refund itself, `refund_reason` on the three payment responses says why the settler gave up when it said so, and `PaymentTransactions.refund` is the refund transaction. `isTerminalStatus` treats `refunded` as terminal, so `waitForTerminalStatus` stops on it. `refund_available` is not terminal: the funds are still in escrow until the refund lands or a late delivery is paid. `send-payment` exits 4 on `refund_available` and 3 on `refunded`, and `--wait` does not wait on a payment that is already `refund_available`.
- **The default quote deadline is now 3 seconds** for both `preparePaymentRequest` (was 10) and `prepareQuoteRequest` (was 5), and so for `send-payment` and `request-quote` as well. Bidding closes at the quote deadline and the gateway always waits until then, so a payment or quote request that relies on the default now spends about 3 seconds at the quote step instead of 5 to 10. `DEFAULT_PAYMENT_QUOTE_DEADLINE_SECONDS` and `DEFAULT_QUOTE_DEADLINE_SECONDS` are both `3`, and the API description's default for `quote_deadline_seconds` on `PreparePaymentRequest` is `3`. The window has to cover signing and submitting the request as well as settlers quoting, and a signed request is submittable only before its quote deadline. Pass a larger `quoteDeadlineSeconds` (`--quote-deadline-seconds` on the command line) when signing takes longer, for example a signer that waits for an approval, when you submit the request later, or when your clock lags the gateway's. Passing the old value restores the old window.
- **Breaking: the three Atum credential contexts moved to `schemas.atum.xyz`.** A holder credential passed to `buildEnvelope` must name `https://schemas.atum.xyz/credentials/known-to-atum/v1`, `.../kyc/v1` or `.../sender-compliance/v1`. Their terms moved with them, for example to `https://schemas.atum.xyz/credentials/known-to-atum/v1#role`, and those term IRIs are what a credential's signature covers. A credential that still names a `https://schemas.atum.network/credentials/...` URL is refused as an unknown JSON-LD context. One issued under the old vocabulary does not verify even with its URL rewritten, so it has to be re-issued.
- `FulfillmentAuthorization.authorization` now documents the EIP-3009 shape the settler signs: the transfer is in `message_prehash` as typed-data JSON, `message` is its EIP-712 digest, there is no `payload`, and `validBefore` is the payment's `fulfillment_deadline` in whole seconds. The type is unchanged.
- **Breaking: `preparePaymentRequest` and `prepareQuoteRequest` refuse a `requestId` outside `^[A-Za-z0-9._-]{1,128}$`**, before anything is built: 1 to 128 ASCII letters, digits, `.`, `_` or `-`. The payment request is now read with the strict reader that computes depositRequestHash v2, whichever version is signed, and that reader, like the gateway once it enforces v2, takes no other `request_id`. Ids the CLI generates already conform; a `--request-id` or `--request-id-prefix` outside the pattern is refused. More generally, any body the strict reader refuses now fails at build, whichever version is signed, not only one with such a `request_id`: for example `settlerRequirements` carrying a member other than `whitelist` and `blacklist`, which the schema allows.
- `preparePaymentRequest` builds the whole request body before the deposit authorization and signs over exactly that body, then adds `sender_auth` to it. The output for v1 is unchanged.
- `CommitmentOutcome` gains `quote_request_mismatch`, from the shared SDK's new quote binding. A `Record` or exhaustive `switch` over the outcomes needs a branch for it.
- `verifyPaymentRequest` is deprecated: it checks a parsed copy of the request and accepts only depositRequestHash v1, and refuses a `depositRequestHashV2Mode`. Use `verifyPaymentRequestJSON` with the request as received.
- **Breaking for TypeScript callers: `fulfillment_verifier` and `escrow_contract_address` are required on `PaymentRequest` and `CreateQuoteRequest`.** The gateway already refuses a request that omits either. The types said optional with a default the gateway never filled in. Take both from `GET /v1/defaults` for the source chain. `preparePaymentRequest` and `prepareQuoteRequest` already set them, so a caller using the builders is unaffected. The gateway also requires `message_prehash` on every `sender_auth.signed_messages` entry; `SignedMessage` keeps it optional because the award and fulfillment authorization shapes share that type.
- **Breaking: `preparePaymentRequest` requires `maxSourceAmount`.** It used to default an omitted cap to `fulfillment_amount` plus 2 bps in raw units and sign that into the Permit2, without either token's decimals or price. Across assets with different decimals or value, the signed ceiling could be orders of magnitude above what the payment was worth. The cap is now required in the type and at runtime, must be a positive base-10 integer in the source token's smallest units, and is checked before any network call. Derive it from a settler quote with `capFromQuote`, or state it explicitly. `send-payment` gains `--max-source-amount`, required when building a payment.
- **`prepareQuoteRequest` no longer invents `max_source_amount`.** An omitted cap used to be derived from `fulfillment_amount` plus 2 bps in raw units, which ignored both tokens' decimals and price: across assets it either filtered nothing or filtered every honest quote. An omitted cap is now left off the request, which the gateway reads as no cap. A supplied cap must be a positive base-10 integer in the source token's smallest units; anything else throws. A caller that relied on the implicit filter should pass `maxSourceAmount` explicitly.
- **Breaking: the builders for retired escrow shapes are removed.** No deployed escrow accepts what they produce. Removed: `createPermitWitnessTransferFromPrehash`, `PermitWitnessTransferFromParams`, `hashRequestId`, `createTvmPermitWitnessTransferFromPrehash`, `TvmPermitWitnessTransferFromParams`, `createSolanaDepositPrehash`, `hashSolanaDeposit`, `generateSolanaPaymentId`, `SolanaDepositParams`, `SolanaDepositPrehash` and `DEPOSIT_MESSAGE_SIZE`. Build payments with `PaymentGatewayClient.preparePaymentRequest` and sign them with `signPaymentRequest`; `hashPermitWitnessTransferFrom`, `hashTvmPermitWitnessTransferFrom` and the address and nonce helpers remain.
- **Breaking for TypeScript callers: `destination` and `requestId` are removed from `VerifyPaymentRequestExpectations`.** The payee check they switched on is now always on, and it takes both values from the request itself.
- **Breaking for TypeScript callers: `depositWitnessVersion` is removed from `ChainDefaults`.** Every deployed escrow uses the four-member deposit witness, which is now the only one built, so the gateway's `deposit_witness_version` is no longer read. Building a Solana payment fails for an `svm_signature_domain_version` below 4.
- `deposit_witness_version` is removed from the `GET /v1/defaults` response in the API description and the generated wire types. The SDK builds only the four-member witness.
- A payee-check refusal throws an error whose message names its outcome, for example `sender_auth: destination_mismatch: ...`. `ParsedPermit.destination` and `depositRequestHash` are now set on every chain.
- New `verifyPaymentRequestJSON` checks a request from its JSON text and also refuses a repeated member name, including names that differ only in letter case, where it is read: any top-level name, or inside `source`, `destination`, `request_id` or `sender_auth`. New `commitmentResultOf` reads the outcome and both copies of the payee from a refusal, and each verified entry carries the same result as `commitment`.
- Each value a verifier reads has one accepted spelling: `message` is `0x`-prefixed hex on every chain, Tron included; a signature is `0x` followed by 65 bytes of hex (recovery id 0, 1, 27 or 28) on EVM and Tron and `0x` followed by 64 bytes on Solana; and `max_source_amount` is a decimal integer with no sign, prefix, padding or leading zero.
- New `verifyRequestCommitment` checks the payee and request id a deposit commits to without recovering the signer, so it serves contract-account payers (ERC-1271, such as a Safe). `verifyPaymentRequest` and `verifyPaymentRequestJSON` recover every signer and so accept key-account payers only.
- A Solana deposit may omit `delegate_signer`; the signature is then checked against `source.account`. When present, it must equal `source.account`.
- **Breaking for TypeScript callers: `fulfillment_timestamp` is optional on `FulfillmentConfirmation`.** The gateway stopped sending it on 28 August, when settlement moved onto the settler's own report and the path that read the fulfilled event's block time was removed. The settler's report carries no time, so the field is simply absent from every confirmation. The type said `string`, so a caller reading it got a value the compiler promised and the runtime never delivered, and a client generated in a language that enforces required fields failed to deserialize a **completed** payment, after the money had moved. It is now `string | undefined`, which is what arrives. A caller that reads it gets a compile error and has to handle the absence; a caller that ignores it is unaffected. It will become required again when the settler reports the destination block time, and widening it back is not a break.
- **`request_id_reusable` is new on every error shape**, on `ErrorResponse` and on the asynchronous `PaymentFailure`. `retry_classification` was answering two questions at once: what the caller must change, and whether their own `request_id` survived. A malformed body and an unserved corridor are both `NOT_RETRYABLE_FIX_REQUEST`, and only the first leaves the id free, so the enum could not say both. `true` means no payment was created and the id can be re-sent; `false` means a payment exists and re-sending only replays that outcome. Absent means undetermined, which a caller should read as `false`, since assuming an id is free when it is not is the direction that costs an attempt.
- **Several public error codes changed value**, so a caller branching on the string needs the new ones. `CONFLICT` split into `ALREADY_SETTLED`, `DUPLICATE_INTENT`, `PAYMENT_IN_PROGRESS` and `REQUEST_ID_TAKEN`, because one code meant four different required actions: read the result, reconcile, poll, or start over with a new id. `INTERNAL_ERROR` split off `SETTLEMENT_OUTCOME_UNKNOWN`, which means settlement had started and money may already have moved, as distinct from a fault where nothing happened. `RATE_LIMITED` and `REQUEST_TIMEOUT` are gone: nothing emitted them. Every one of these keeps its HTTP status and its `retry_classification`, so the code string is the only signal that anything moved. **A caller matching `CONFLICT` keeps compiling and keeps receiving 409, then falls through to its default branch** — and for an already-settled payment that can mean re-submitting one that has been paid.
- `METHOD_NOT_ALLOWED` is a new public code. A wrong HTTP verb was reported as a missing route, which sends an integrator looking at their URL instead of their method. A 405 now also carries the `Allow` header naming the methods the target does support.
- **Breaking: `PaymentStatus` is one type across all three payment responses**, with the values `pending`, `finalizing`, `completed` and `failed`. Submitting a payment, polling its status and reading its timeline previously returned three unrelated status types, so a caller could not write one function that handled "a payment status". `settling` is gone — it described how far our own bookkeeping had got, not the payment. `cancelled` is gone too: nothing could produce it, and a payment that ends without being delivered is reported as `failed`. `isTerminalStatus('cancelled')` therefore returns `false` now. A caller with an exhaustive `switch` on status gets a compile error and has to add a `finalizing` branch; a caller testing only for `completed` or `failed` is unaffected.
- **`finalizing` is new, and is NOT terminal.** It means the transaction paying the recipient is on chain and accruing the confirmations its chain requires — made, but not yet irreversible, much as a card authorization is not a settlement. It normally becomes `completed` and can still become `failed`. Nothing emits it yet; it is declared here so clients are ready before the gateway starts sending it.
- **Breaking: one failure shape.** `PaymentError` and `TimelineError` are replaced by a single `PaymentFailure` used by all three responses, so a failure reads identically however you ask about the payment. On the timeline that is a real change of shape: `chain_id`, `tx_hash` and `revert_reason` were flat on the error and are now nested under `blockchain_context`, which also carries the four fields that endpoint previously discarded — the block number among them.
- **Breaking: `tx_hash` is now `transaction_hash`**, on `error.blockchain_context` (all three responses) and on `steps[]` (timeline). This is the name the shared error shape and the rest of our published specs already used; the payment API was the outlier. **A caller reading `error.blockchain_context.tx_hash` gets `undefined` after upgrading** — there is no deprecation period because the field moved to the shared definition rather than being duplicated under both names.
- `PaymentFailure` now carries `docs_url` and `retry_classification`. Both were already computed for every error code but only ever reached failed *requests*, never failed *payments*.
- The `payment-outcome` CLI no longer maps `cancelled` to exit code 3 (terminal failure), because the gateway no longer reports it. A status this build does not recognise exits 2 (still pending), which is the safe direction: a script that waits one more round costs a poll, a script that gives up on a live payment can cost a second charge.
- **New `transactions` object** (`deposit`, `fulfillment`) on all three responses, for looking a payment's on-chain transactions up yourself. Declared but not yet populated.
- The package moved within the protocol repository, from `payment-gateway-client/` to `schemas/apis/payment-gateway/v1/bindings/payment-gateway-client/`, beside the other payment-gateway bindings. Only the manifest `homepage` and `repository.directory` change; the published name, entry points and behavior do not.

### Fixed
- `preparePaymentRequest` and `prepareQuoteRequest` stamp the quote and fulfillment deadlines after their own network reads, the chain-defaults fetch and, for a Solana source, the cluster-clock read, so that time no longer comes out of the quote window. Invalid deadline values are still refused before any network call.

### Security
- `verifyPaymentRequest` refuses a request whose payee or `request_id` differs from the one the payer signed, on EVM, Tron and Solana. A request's `destination` and `request_id` fields are not covered by the payer's signature; the copies inside the signed deposit are, and the two must now agree. A deposit that commits no destination is refused.
- The HTTP client is now axios 1.20.0. 1.13.2 had a run of advisories (prototype-pollution gadgets that could tamper with requests or responses, proxy-authorization leaks, NO_PROXY SSRF, ReDoS). A caller that pins axios independently should take 1.18.0 or newer. A timeout that fires after headers have arrived still surfaces as `GatewayTimeoutError`: axios 1.20 attaches the partial response, and the client drops it so a stalled error body is not reported as a completed HTTP status.

## [3.0.0] - 2026-09-16

> **Read this before upgrading if the gateway has been accepting your asset identifiers.**
> They are now validated locally, on both entry points and on both legs of the payment. One rule
> is stricter than the gateway's, the EIP-55 checksum on a mixed-case EVM token address, so a
> value the gateway resolves fine can be refused before the request is even built. See Breaking.
>
> A second break sits there too. A blank `pinnedAddress` is now rejected rather than skipping the
> sender check, so a caller that defaults that field to an empty string has to pass the sender
> address instead, or omit the field to skip the check on purpose.

Quote-requests now carry the same idempotency contract as payments: one `request_id`
identifies one batch, re-sending it recovers that batch, and reusing it for a different
corridor is refused rather than silently served.

### Breaking
- Asset identifiers are validated on every entry point. `prepareQuoteRequest` built no deposit and so applied no address rules at all, and `preparePaymentRequest` applied them only to the source, since only the source reached a chain library. Both legs of both entry points are now checked, so a value that used to be forwarded can now be refused locally, with the messages under Fixed: a malformed or wrongly-checksummed EVM token address, a placeholder such as `erc20:0x6`, a native `slip44` asset, a malformed Tron or Solana token reference, or a hex `eip155` chain id. Every segment is also checked against the character set the PaymentRequest schema publishes, so a stray space is refused here rather than remotely.
- **A mixed-case EVM token address whose EIP-55 checksum does not hold is refused on the destination leg too, and that is deliberate.** The gateway tolerates such a destination on purpose: `blockchain.AssetIdentifier.Equal` folds the case of an eip155 token address with `EqualFold`, the token registry lowercases before it looks a token up, and `payment-gw/internal/canonical` folds a destination it could not parse rather than refusing it, precisely so two spellings of one destination cannot refuse a legitimate retry. The settler lowercases before it checksums, so a wrong checksum settles fine. This rule therefore buys no settlement safety. It is typo protection while the request is still being built, kept fatal because a mistyped token address is cheap to catch here and expensive to discover once a payout has landed on it. It is narrow on purpose: the destination account is not checked, so this is not a claim that the client validates the receive side. A caller that can rewrite the value should send the all-lowercase form of the destination, which makes no checksum claim, is accepted, and is the same twenty bytes. A caller whose corridor is composed inside a library that builds the request for it, as in `mppx-atum-escrow`, has nothing to rewrite, and the lowercasing belongs there.
- **Behaviour change.** An empty `pinnedAddress` is now rejected before anything is signed or submitted, on both signing providers. It previously counted as omitting the field, so the check that the sender is the signer's own address was skipped: the Turnkey path forwarded the pin only when truthy, and the private-key path gated its key-derivation check the same way. What that produced depended on the caller. `send-payment` derives the depositor from the same `<sender>` argument, so the payment went out with an empty source account for the gateway to reject. An SDK caller that supplies `depositor` and `pinnedAddress` separately got a valid, settleable payment whose sender was never checked against the wallet or the key, which is the case this closes. A call that previously proceeded now throws, so a caller defaulting the field to `''` needs to fall back to the sender address instead. Omitting `pinnedAddress` still skips the check as before.
- `prepareQuoteRequest` now **requires** `requestId`, and `requestIdPrefix` is gone. It
  previously generated an id when you omitted one, on the grounds that the id was only a
  correlation handle there — which is no longer true, because it is now the idempotency key.
  Generating one for you meant a rebuilt retry quietly opened a **second** batch and left the
  first unreachable. `preparePaymentRequest` has always required it; the two now match. The requirement is
  enforced at runtime as well as in the type, so an untyped JavaScript caller or an empty
  string throws rather than sending a request with no idempotency key. Pass
  your own stable id, and reuse it to retry. The `request-quote` CLI is unaffected: it
  generates an id when `--request-id` is omitted and prints it back, exactly as `send-payment`
  does.
- `QuoteRequestResponse.idempotent_replay` and `QuoteRequestAccepted.idempotent_replay` are new
  **required** fields. Reading a response is simpler, not harder — the flag is always present,
  so `false` means `false` rather than "maybe an older gateway".
- **The error `domain` value `SOLVER_GATEWAY` is now `SETTLER_GATEWAY`.** It names the service that runs the settler auction, which is a settler gateway; the old name was left over from earlier terminology and was the only place the word "solver" still reached callers. Code that switches on `AtumError.domain` and has a `'SOLVER_GATEWAY'` case must rename it — nothing else about the error changes, and `domain` is diagnostic metadata rather than something the payment flow branches on, so most callers are unaffected. The public `code` and `message` on an error are unchanged: the internal codes behind this domain already mapped to the public `SERVICE_BUSY` and `INTERNAL_ERROR`, and still do.

### Added
- **`ensureSourceApproval` and `needsSourceApproval`**, so the Permit2 prerequisite this package has always stated can now be satisfied from it. Paying from EVM or Tron needs a one-off approval of the source token for Permit2; without it a payment is built correctly, signed correctly, accepted by the gateway, and then reverts on-chain at settlement — the most expensive way to learn about a missing allowance. Until now the README and `send-payment --help` named the requirement and offered no way to meet it. `ensureSourceApproval` reads the current allowance and sends an approval only if it falls short; `needsSourceApproval` answers the same question read-only, spending no gas, so a payer can be warned before being asked to sign. Solana reports that no approval is needed rather than doing nothing, since its deposit authorizes the transfer itself. **This is the first part of this package that broadcasts a transaction and spends gas.** Everything else builds and signs offline, and that has not changed: you pass a connected ethers signer (or a TronWeb instance for Tron), so the package still never chooses an RPC endpoint or holds a key. An approval is unlimited by default, so later payments need no further transaction; `approvalAmount` bounds it instead, at the cost of having to renew it as Permit2 consumes it — pair a bound with `requiredAllowance` across repeated payments, or the bound stops covering itself as soon as the first charge is decremented from it. Waiting for the approval to confirm is bounded by `confirmation.timeoutMs` (one minute by default) rather than indefinite, and `onSubmitted` hands you the transaction hash the moment it is broadcast. Tokens that refuse to overwrite a non-zero allowance — mainnet USDT most notably — are reset to zero first, but only where the token actually demands it. An approval is refused outright when the signer you pass does not hold the `owner` account whose allowance was read: an approval only ever applies to the account that sends it, so a mismatched signer would approve that account, hand back a transaction hash that reads as success, and leave the owner exactly as unable to pay as before. The read-only `needsSourceApproval` is unaffected, since asking whether a payer is ready without holding their keys is a legitimate preflight. `isUnconfirmed` ships alongside them for telling a broadcast-but-unseen approval apart from one that failed: the wait for a confirmation is bounded, and reaching that bound is not a failure, so the two need opposite responses. `approve-permit2` reports an unconfirmed run as `{"unconfirmed": true, "txHash": ...}` on stdout rather than as a bare non-zero exit indistinguishable from a revert. These helpers raise an allowance and never lower one, so `--amount` below an allowance the wallet already holds leaves it alone and says so.
- **`approve-permit2`**, a command that performs that approval. `approve-permit2 <sender> <sourceAsset> --rpc-url <url>` takes the same CAIP-19 asset string as `send-payment`, and `--check` reports whether an approval is needed without sending anything or needing a key. It is a separate command rather than a flag on `send-payment` because it is a different kind of act: it spends gas, once per wallet and token, and is worth doing deliberately and ahead of time rather than as a side effect of paying. The private key comes from `PRIVATE_KEY` or an interactive prompt and is never accepted as a flag, which would put it in shell history and in the process list. EVM and Tron; Tron additionally needs `tronweb`, an optional peer dependency, so that EVM-only installs do not carry it. The result JSON goes to stdout, like the other commands. The allowance is read before a key is ever requested, so an already-approved wallet — which is every wallet after the first run — never has to produce a secret to learn there was nothing to do, and the key is checked against `<sender>` before anything is sent, so a mismatched key cannot approve the wrong account and report success.
- **Signing helpers for all three PaymentRequest signatures**, available from the `@atum-labs/payment-gateway-client/signing` subpath. A PaymentRequest carries three unrelated signatures and choosing the wrong one is the mistake this surface exists to prevent, so they are named for what they authorize rather than for how they are built. `signPaymentRequest` fills `sender_auth.signed_messages[]` and authorizes the **on-chain transfer**. `signDeclaration` attests that the **document** came from its signer, as a W3C Data Integrity proof over the URDNA2015-canonicalized request — it is exported under that name, rather than the upstream library's `signPaymentRequest`, precisely so the two cannot be confused. `buildEnvelope` and `buildEnvelopeForAccount` carry the **originator's identity** as a holder-signed PaymentRequestEnvelope. Signing one does not stand in for another: a request with a valid `sender_auth` and no envelope authorizes a transfer by an unidentified originator, and the reverse identifies an originator who has authorized nothing. Every one of them takes a **signer, never a private key** — a hex key would force raw key material into a JavaScript string that cannot be zeroized, is copied on assignment, and lands in heap snapshots and any log line that stringifies the surrounding object, and it would exclude every custodian whose key sits in a KMS or an HSM. `signerFromEthersWallet` covers a local key; a custodial signer implements `signDigest` over its own call. The signature contract is 65 bytes of `r || s || v` with **v ∈ {0, 1}**: a signature whose v is already 27 or 28 is refused, because applying the alignment twice recovers a *different* address, which is a well-formed signature that verifies as somebody else. Also exported: `computeRequestHash`, `verifyDeclaration` (which **throws** rather than returning a flag, and refuses a document whose signature recovers a signer other than the one it claims), `verifyPaymentRequest` for checking what a `sender_auth` signature actually commits to before submitting, `didForAccount`, `verificationMethodForAccount`, and their types. See `docs/signing.md`.
- **`jsonld` is a new dependency**, and it is pinned exactly rather than floating. It runs URDNA2015, the canonicalization that determines exactly what a signature covers, so a minor release that changed its output would change what customers sign, on their machines, with nothing in our CI to notice.
- **`send-payment --prepare-only` and `send-payment --submit <file>`** split the single-shot command in two. `--prepare-only` builds and signs a payment request, prints it to stdout, and stops without submitting; `--submit` sends one that was prepared earlier (`-` reads stdin, so the two pipe together). Together they turn the single-shot command into an inspect-then-approve flow: the printed document is byte-for-byte what that run would have POSTed, so it can be read and reviewed before any money moves. Treat it like a signed cheque: it is a signed authorization rather than a draft and `--submit` needs no key, so delete the file once the payment is sent or abandoned. Re-preparing under the same `request_id` targets the same payment and cannot pay twice, but does not reproduce the same bytes: the deadlines are stamped from the clock on each run and the signature covers them. Two things to know. `--prepare-only` still calls the gateway, which is where the corridor addresses come from, so it is not an offline signing mode. And the exit-code table describes a *submitted* payment, so it does not apply under `--prepare-only`, where `0` means the request was built and signed and no payment exists — do not chain a payment-conditional step off such a run. If you intend to submit later, widen the quote window with `--quote-deadline-seconds` — but by tens of seconds, not minutes. A prepared document is submittable only while its window is open (the default is 10 seconds), and that same window is the settler auction: the gateway waits it out before selecting, and settler quotes expire on their own, so an over-long window ends in a terminal `QUOTES_EXPIRED`. `--submit` signs nothing and needs no private key, takes no corridor arguments, refuses the options that only shape a request being built rather than ignoring them, and reports with the same exit codes and streams as an ordinary run; it supports `--wait` the same way. The two flags are mutually exclusive, and a short invocation now names both forms rather than reporting a missing argument.
- The Permit2 approval prerequisite now appears at the top of `send-payment --help`, above the arguments and options, instead of in the last paragraph. It is the most common cause of a payment that is built and signed correctly and still fails to settle, and it was previously about a hundred lines below the usage line. The contract addresses stay at the end of the help, where the prerequisite points.
- **`waitForTerminalStatus` and `isTerminalStatus` are exported**, so following a submitted payment to its end is one call rather than a hand-written loop. A submission usually comes back `pending`, so waiting is the ordinary path, and the previous answer — write your own poll — put the burden of getting it right on every caller. A failed status check does not end the wait: a blip while a payment is settling is the worst moment to stop looking, so failures are counted in `errorCount`, reported through `onError`, and polling continues to the budget. The outcome reports `timedOut` so a caller can tell "still in flight" from "finished", which a bare loop cannot. This is the same helper behind the `send-payment --wait` flag, so the command-line tools and the SDK now agree by construction. `isTerminalStatus` is the single definition of which states are final, so a caller no longer keeps its own copy of that list in step with the contract. `budgetMs` is optional and in milliseconds, defaulting to `DEFAULT_WAIT_BUDGET_MS` (one minute); the seconds-based constant behind the command line's `--wait-seconds` stays internal, so there is one unit on the public surface and no way to pass 60 where 60000 was meant. An optional `signal` ends the wait early for a caller that must stop on shutdown or when its request is cancelled, and the outcome reports `aborted` — which always implies `timedOut`, so an interrupted wait can never be read as a settled payment. Also exported: `DEFAULT_WAIT_BUDGET_MS`, `DEFAULT_POLL_INTERVAL_MS`, `StatusSnapshot`, `WaitOutcome`, `WaitParams`.
- **`ErrorResponse.payment_id`**, alongside the existing `request_id`. The two ids are independent and either can be absent: `request_id` correlates the HTTP call, and `payment_id` names the payment the error was raised against. It closes a real mislabel. A settlement failure on `POST /v1/payments` was returning the payment id in `request_id`, because that was the only id field the shape had, so a caller who trusted the field name and looked the value up as a request id found nothing. Read `getErrorResponse(err)?.payment_id` and reconcile with `GET /v1/payments/{paymentId}/status` before retrying, because a failed settlement leaves the on-chain outcome unguaranteed. The field is absent whenever the error is not about a specific payment, which is every validation or authentication failure raised before a payment exists.
- `parseAssetIdentifier` and `assetChainId` are exported, so a caller can apply the same parsing and canonicalization the CLIs do.
- `timeoutMs` and `syncWaitTimeoutMs` on the client config, for callers whose gateway is slower than the defaults (30s for a promptly-answered request, 120s for one the gateway holds open). The two are separate because some endpoints are held open on purpose, bounded by the gateway's own `quote_sync_wait_seconds` and `payment_sync_wait_seconds`, so one budget cannot serve both: too short aborts a settling payment, too long leaves an unresponsive gateway hanging. An interceptor that sets `timeout` still takes precedence, for a per-request override. New exports: `GatewayTimeoutError`, `isGatewayTimeoutError`, `PaymentGatewayClientConfig`, `RequestTimeouts`, `DEFAULT_REQUEST_TIMEOUT_MS`, `DEFAULT_SYNC_WAIT_TIMEOUT_MS`.
- `createQuoteRequest` returns **`409` `IDEMPOTENCY_TERMS_MISMATCH`** when a `request_id` is
  reused with different economics (accounts, assets, or amounts), instead of returning the
  first batch. Without it you could receive quotes priced for the corridor you asked for
  earlier, and awarding one of those settles a payment on that corridor.
- `idempotent_replay` on both quote-request responses tells you whether you were handed an
  existing batch or a newly opened one.

### Changed
- `resolveTurnkeyAddresses` takes its Turnkey config without `pinnedAddress`. That call lists the wallet's accounts and verifies nothing, so a pin handed to it was ignored. Passing one inline is now a compile error instead of a check that never ran. A caller reusing one whole `TurnkeyConfig` for both this call and signing is unaffected.
- The CLIs no longer print the full gateway defaults listing when a chain-defaults lookup fails. The failure itself names the chain and carries the gateway's error, and the client no longer makes the second `/defaults` request that fetched the listing.
- Re-sending a quote-request whose `quote_deadline` has already passed now returns the original
  batch instead of `400 QUOTE_DEADLINE_NOT_FUTURE`. The collection window is short, so a retry
  after a lost response almost always carries an expired deadline — previously that made the
  `quote_request_id` unrecoverable even though the batch existed and held quotes. Deadlines are
  exempt from the idempotency comparison, on this endpoint as on payments.
- Note the window itself is not extended: it belongs to the batch, so asking again with a later
  `quote_deadline` returns the batch's own window.
- `docs/idempotency.md` is reorganised around the shared contract rather than the payment
  endpoint, with the endpoint-specific parts (the on-chain settlement guarantee, payment status)
  labelled as such.
- The `409 IDEMPOTENCY_TERMS_MISMATCH` message no longer says a *payment* exists. It previously
  read "already used for a payment with different terms", which is wrong on quote-requests —
  nothing is charged there and no payment exists for the caller to go looking for. It now says
  "already used for a different request". This affects the payments path too: the wording is
  slightly less specific there, in exchange for being correct on both. The `code` and the docs
  link are unchanged, so nothing a client branches on has moved.
- The asynchronous (202) quote-request response now says plainly that its `status` field is a
  constant rather than a report of the batch's state: on an idempotent replay the window may
  already have closed and it will still read `collecting`. Points at
  `GET /v1/payments/quote-requests/{quoteRequestId}` instead. Documentation only.

### Fixed
- A malformed asset identifier is reported with the offending value and what to correct, instead of surfacing as a chain-library error. A missing `/` between the chain and the token says `Invalid asset identifier "<value>": expected CAIP-19 "<chain>/<type>:<address>", e.g. eip155:421614/erc20:0x...` where it previously threw `TypeError: Cannot read properties of undefined (reading 'split')`. An empty token or a stray slash says `Invalid token address in asset "<value>".`, and a mixed-case address whose EIP-55 checksum does not hold says `Token address "<addr>" has an invalid checksum. Fix the capitalization or use the all-lowercase form.` Those were `invalid address` and `bad address checksum` respectively, from `ethers`. Two cases name their real cause rather than the address they were also reported as: a hex `eip155` chain id says `Invalid eip155 chain id "0x66eee" in asset "<value>": use the decimal chain id (421614), not hex.` and any other non-decimal reference says `Invalid eip155 chain id "<reference>" in asset "<value>": an eip155 chain id is decimal, e.g. 421614.`, while a native asset says `Asset "<value>" is a native asset (slip44) and has no contract to deposit. Use the wrapped token's erc20 identifier.`
- An identifier whose CAIP-2 namespace is not lowercase (`EIP155:42161/...`) is routed rather than refused as an unsupported chain. Both namespaces are canonicalized to lowercase in the request the client builds and in the deposit it signs, which is what the PaymentRequest schema requires, so such a request is no longer rejected by the gateway either.
- A Tron chain reference is folded with the namespaces, mirroring the protocol's own `manifest.CanonicalizeCAIP2`, so `TRON:MAINNET/trc20:...` routes instead of failing inside the sender_auth SDK with `no Permit2 address known for Tron network`. A Solana reference is still left alone: it is base58, and its cluster name is UTF-8 encoded into the escrow's on-chain `cluster_id`, so folding it would change the signing domain.
- A failed chain-defaults lookup reports the gateway's own `code`, `message` and `request_id` instead of the HTTP status text, which reduced every cause to `Bad Request`.
- A non-integer value for `--quote-deadline-seconds`, `--fulfillment-deadline-seconds` or `--wait-seconds` (for example `1.5`, `1e3`, `0x10`, or plain text) now prints the one-line reason and exits `1`, instead of a full Node stack trace. The CLIs already refused to run with such a value and the exit code is unchanged; only the output is. The option parser runs before the command's error handling, so what it threw had been escaping uncaught.
- A whitespace-only `pinnedAddress` was not skipped but reported as an address mismatch, so the error named a padded value rather than the actual problem. It now gets the same up-front rejection as an empty one.
- `send-payment` validates `<sender>` before prompting for a private key, so a blank argument no longer costs the user an entered secret first.
- Gateway requests now time out instead of hanging. The client had no network timeout: the chain-defaults call used a bare `fetch` with no abort signal and the HTTP client set none, so a gateway that accepted the connection and never replied left the CLI waiting indefinitely with nothing on stdout or stderr. Requests now abort and raise a `GatewayTimeoutError` reading `Gateway at <url> did not respond within <n>s`. The abort covers the response body as well as the headers, so a gateway that returns `200` and then stalls is caught too, as is one that answers a chain-defaults failure and then stalls the error body the message is read from.
- **The Solana signing format in the published types was wrong.** `SignedMessage.message` was documented as a base64-encoded message on Solana, where the value the network verifies is the hex-encoded message hash with a `0x` prefix, as it is on EVM and Tron. A caller following the type's own documentation produced a signature that could not be recovered, and the request was refused with nothing in the message pointing at the encoding. The description now matches the format that is signed and verified. Types and runtime behaviour are unchanged; only what the types say about them.
- `SenderAuthMessageScheme` documents `EVM_PERMIT2_ESCROW`. The value has always been accepted and appeared in the type's union, but the accompanying description listed only the other three, so the one scheme that pairs a gasless approval with escrow support read as undocumented.
- `SenderAuth.verifiable_credential` is marked deprecated in the published type, which it already was in the format that is signed. Credentials belong in the holder-signed `PaymentRequestEnvelope`; the inner request carries none, and its Data Integrity signature excludes this field. A caller still populating it can see that from the type now rather than only from the signing schema.

## [2.2.0] - 2026-08-04

> **Read this before upgrading if you script `send-payment`.** Its exit codes now
> distinguish a settled payment from one still settling and one that failed, where every
> accepted submission previously exited `0`. See the first entry under Changed.
>
> One typed-API change: three fields on `PaymentResponse` are no longer optional. This makes
> reading a response simpler, not harder — see Changed.

### Added
- `send-payment --wait` keeps checking a submitted payment until it settles or fails, instead of reporting it as still pending. `--wait-seconds <n>` sets how long (default 60). With `--wait` the JSON on stdout is printed once the wait ends and reports the payment as of the last check — so it carries the settled `status` and the `fulfillment_confirmation`, rather than the `pending` the submit returned. Without `--wait`, output is unchanged. The bound is a client-side convenience: giving up does not affect the payment, and re-submitting the same `request_id` or reading the status endpoint picks up wherever it got to. A settlement that stalls never becomes terminal on its own, so no bound can promise a terminal answer.
- `send-payment` and `payment-status` now print a one-line outcome summary to stderr saying what the payment's state means for a re-attempt: a pending payment is collected by re-submitting the **same** `request_id`, while a terminally failed one keeps its id and needs a **new** one. The JSON on stdout is unchanged.
- Documented in `docs/idempotency.md` and the README: what the `409` compares, that deadlines and the signature are exempt from it, `idempotent_replay`, how to read `status`, and that a direct caller may either poll the status endpoint or re-submit.

### Changed
- **Behaviour change — `send-payment` exit codes.** Previously any accepted submission exited `0`. Now `0` means `completed`, `2` means `pending`, and `3` means `failed`/`cancelled`; `1` continues to mean the payment could not be submitted. Previously a still-settling payment and a terminally failed one both exited `0`, so `send-payment ... && <next step>` ran the next step for a payment that had not settled — including when re-submitting a `request_id` whose payment had already failed. Scripts that treat `0` as "submitted" should treat `0` and `2` as "submitted"; scripts that mean "settled" now get that from `0` alone. `payment-status` is unaffected: as a lookup, its exit code reports whether the lookup worked.
- `--request-id`'s help text now states the consequence of omitting it: an id is generated, which makes every bare re-run a separate payment rather than a retry.
- **`PaymentResponse.payment_id`, `.status` and `.idempotent_replay` are now required** in the typed API, matching what the gateway has always sent. They were typed optional, so TypeScript reported them as possibly `undefined` and reading `idempotent_replay` meant writing `=== true` to satisfy the compiler for a value that is always present. Existing code keeps compiling — a narrowed type only removes checks — unless it constructs a `PaymentResponse` itself, as a test fixture might, in which case all three now have to be supplied.



### Fixed
- Corrected the idempotency documentation. The 2.1.0 note below said that reusing a `request_id` with different terms returns the original payment and silently drops the new terms. The gateway rejects it with `409` `IDEMPOTENCY_TERMS_MISMATCH`, so an integrator following the old text would neither expect nor handle that error.
- `IDEMPOTENCY_TERMS_MISMATCH`'s message described the compared terms as "source, destination, or fulfillment_amount", which had become incomplete — `max_source_amount` is compared too. It now names the categories ("accounts, assets, or amounts") rather than enumerating fields, so it stays accurate as the payment schema grows. The docs describe the comparison the same way, and point at the error's own `message` for which category differed.

## [2.0.0] - 2026-07-27

### Breaking
- `request_id` is now required on `preparePaymentRequest` (the client no longer silently auto-generates one, which could turn a retry into a second payment). Callers must supply a stable `request_id` and reuse it on retry. The `send-payment` CLI generates a one-shot id when `--request-id` is omitted.
- An explicit `deadlineSeconds` that is shorter than the settlement window (`fulfillmentDeadlineSeconds`) is now rejected — the deposit permit must stay valid until settlement.
- Solana now honors an explicit `nonce` (it was ignored on Solana in 1.0.2) and validates it at build time: a caller-supplied nonce must fit an unsigned 64-bit integer and its low byte (the on-chain replay slot) must be `< 235`, otherwise the build throws instead of failing later on-chain. Omitting `nonce` still derives it deterministically as before.

### Changed
- Deposits are now built and signed through the shared `@atum-labs/payment-request-sender-auth` library instead of the client's own copy of that logic (single source of truth across the payment stack). The public signing API (`createSenderSigner`, `signPaymentRequest`, `resolveTurnkeyAddresses`) is unchanged.
- The EVM/Tron deposit permit deadline now tracks the payment's settlement (`fulfillment_deadline`) instead of a fixed far-future date, so the authorization's validity window is meaningful.

### Added
- The deposit's single-use nonce is now derived deterministically from `request_id` + depositor, so rebuilding the same payment (e.g. on retry) reproduces the same single-use nonce. The guarantee differs by chain: on EVM/Tron the Permit2 nonce is a permanent on-chain bitmap, so of any number of rebuilds only one deposit can ever settle; on Solana the escrow replay nonce protects only within a ~128s window (`issued_at` is re-read per build), and the gateway's `request_id` dedup is the durable backstop beyond it — pin `issued_at` via `solanaClockReader` to keep a rebuild inside the same window.
- The depositor address is canonicalized before it seeds the nonce: EVM `0x` addresses are lower-cased (so a checksummed and a lowercase address derive the same nonce), while case-sensitive base58 (Solana/Tron) is used verbatim.
