# CORE-2128 (2026-09-15) — `finalizing` added to the payment status. A payment whose
# transaction is on chain but has not yet reached the confirmation depth that chain
# requires now says so, rather than being called `completed` before that is true. The
# three payment responses share one status vocabulary, so the value is declared on all
# three.
#
# oasdiff reports an added response enum value as a break because a caller written
# against the previous set may not handle the new one, and that is the intended signal:
# a caller branching exhaustively on status should see it and add a branch. `finalizing`
# is not terminal and replaces no terminal value, so a caller that tests only for
# `completed` or `failed` behaves exactly as before.
#
# `settling` and `cancelled` were removed from the status in the same change: neither
# described a state a payment could be in. oasdiff does not report a removed response
# enum value, so they have no lines here.
POST /v1/payments added the new `finalizing` enum value to the `status` response property for the response status `200`
GET /v1/payments/{paymentId}/status added the new `finalizing` enum value to the `status` response property for the response status `200`
GET /v1/payments/{paymentId}/timeline added the new `finalizing` enum value to the `status` response property for the response status `200`

# CORE-2055 (2026-09-16) — `tx_hash` renamed to `transaction_hash`, in three places:
#
#     POST /v1/payments                     error.blockchain_context.tx_hash
#     GET  /v1/payments/{paymentId}/status  error.blockchain_context.tx_hash
#     GET  /v1/payments/{paymentId}/timeline  steps[].tx_hash
#
# These have no oasdiff lines beneath them, and that is the point of writing them here.
# oasdiff does not report a removed OPTIONAL response property, so all three of these pass
# the gate in silence — a caller reading `error.blockchain_context.tx_hash` on the status
# endpoint simply starts getting nothing, with no failure anywhere to say why. They are the
# breaks in this change most likely to reach someone, because /status is the endpoint
# integrators poll, so they are recorded by hand rather than left to the tool.
#
# The rename is not cosmetic. `transaction_hash` is what the shared error shape, the settler's
# own report and two other published specs already call this field; the payment API was the
# one surface spelling it differently, and it is the spelling that has to move for the three
# payment endpoints to share one definition of the block instead of maintaining a copy.
#
# `revert_reason` and `chain_id` also moved on the timeline, from the top of the error object
# down into `blockchain_context` alongside the four fields that endpoint used to discard. Same
# silence from oasdiff, same reason, recorded here for the same reason.
#
# CORE error contract (2026-09-21) — six internal codes now project onto a different
# PUBLIC code, and two public codes are no longer emittable.
#
#     internal                            public was        public is
#     CONFLICT_ALREADY_SETTLED            CONFLICT          ALREADY_SETTLED
#     CONFLICT_DUPLICATE_INTENT           CONFLICT          DUPLICATE_INTENT
#     CONFLICT_DUPLICATE_INTENT_RECOVERY  CONFLICT          DUPLICATE_INTENT
#     CONFLICT_IN_PROGRESS                CONFLICT          PAYMENT_IN_PROGRESS
#     CONFLICT_REQUEST_ID_OWNED           CONFLICT          REQUEST_ID_TAKEN
#     SETTLER_GATEWAY_INTERNAL_ERROR      INTERNAL_ERROR    SETTLEMENT_OUTCOME_UNKNOWN
#
#     no longer emittable: RATE_LIMITED, REQUEST_TIMEOUT
#
# These have no oasdiff lines beneath them, and that is the point of writing them here.
# `ErrorResponse.code` is declared `type: string` with a pattern rather than an enum, so
# a changed public code is not a schema change and the gate passes in silence. This is
# the same class as the CORE-2055 `tx_hash` rename recorded above, and it is recorded by
# hand for the same reason.
#
# Every one of the six keeps its HTTP status and its retry_classification, so the code
# string is the only thing that moved. A caller branching on the old value keeps
# compiling and keeps receiving 409, then falls through to whatever its default arm
# does. For CONFLICT_ALREADY_SETTLED that default is the dangerous one: re-submitting a
# payment that has already been paid. Anyone matching on `CONFLICT` or `INTERNAL_ERROR`
# needs the new values before these services deploy, not after.
#
# The split itself is not in question. One code that meant four different required
# actions could not be acted on, which is why it was split.
#
# CORE error contract (2026-09-21) — `fulfillment_timestamp` became optional on the three
# responses that carry a fulfillment confirmation.
#
# The field has not been sent since 2026-08-28. CORE-2130 (atum-core#1472) moved settlement
# onto the settler's own report, and CORE-2135 (atum-core#1528) deleted the monitor path that
# read the fulfilled event's block time on 2026-09-07. `SettlementResult` carries no time at
# all, so the settler gateway omits the field rather than invent one. Neither of those PRs
# recorded the loss: both describe the confirmation as unchanged.
#
# So this withdraws a promise the service already stopped keeping. It is the direction that
# matters for a caller: a generated client that enforces `required` fails to deserialize a
# COMPLETED payment, after the money has moved, and that is the whole reason for making it
# optional rather than leaving the spec describing a field nobody sends.
#
# Announced together with the public code remappings recorded above, which the same release
# requires telling integrators about. Both go in one message rather than two.
#
# Restoring it needs the settler to report the destination block time, which is a new field on
# SettlementResult plus a per-chain read, since an EVM receipt carries no timestamp. Making the
# field required again at that point is not a break, so nothing further is owed for putting it
# back.

POST /v1/payments the response property `fulfillment_confirmation/fulfillment_timestamp` became optional for the status `200`
POST /v1/payments/awards the response property `fulfillment_confirmation/fulfillment_timestamp` became optional for the status `200`
GET /v1/payments/{paymentId}/status the response property `fulfillment_confirmation/fulfillment_timestamp` became optional for the status `200`

# CORE-2657 (2026-10-05) — `fulfillment_verifier` and `escrow_contract_address` became
# required on the three request bodies that carry a payment request.
#
# The gateway has refused a request missing either field since 2026-09-29. The spec
# described both as optional with a default the gateway never filled in, so this corrects
# the published contract to what the service already enforces. `/v1/defaults` serves both
# values for each chain, and the client's request builders already send them.

# also requires `message_prehash` on every `sender_auth.signed_messages` entry. The shared
# `SignedMessage` component keeps it optional because BidAward and FulfillmentAuthorization

#
# The gateway checks the three fields before schema validation, so a body missing one still
# gets INVALID_FULFILLMENT_VERIFIER, INVALID_ESCROW_CONTRACT_ADDRESS or
# MISSING_MESSAGE_PREHASH, not MALFORMED_REQUEST_BODY. The status stays 400.
